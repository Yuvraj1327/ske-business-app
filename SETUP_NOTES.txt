THREE FEATURES — SETUP AND VERIFICATION NOTES
============================================================

No database migration needed for this delta — all 3 features build on
tables/columns that already existed (picklists/payments/customers/imports
from earlier migrations). Just deploy the backend + Flutter changes.

------------------------------------------------------------
1. DASHBOARD: "Payments Received" tap-to-breakdown
------------------------------------------------------------
Tapping the card now opens a sheet showing Cash / UPI / Bank Transfer /
Cheque totals for the SAME date range currently selected on the dashboard,
reusing the existing GET /reports/payments endpoint (zero new backend
code) — plus the current Outstanding total, labeled "Credit / Not yet
collected". This is deliberately NOT a 4th "collection method" bucket:
by design, a Credit/Udhaar delivery never creates a Payment row (see the
picklist workflow), so it can't appear in a payment-method breakdown — it
shows as Outstanding instead, which is the accurate picture.

------------------------------------------------------------
2. IMPORT HISTORY: delete records
------------------------------------------------------------
Each row now has a delete icon -> confirmation dialog -> DELETE
/imports/{job_id}. This removes ONLY the history/tracking record. Business
data that import already created (customers, sales, picklists) is NEVER
touched. If a Picklist references the deleted import job, that reference
is set to NULL first so the picklist itself survives untouched.

------------------------------------------------------------
3. SETTINGS -> RESET DATA (admin only) — read this carefully
------------------------------------------------------------
Flow implemented exactly as specified: Settings -> Reset Data -> Warning
-> Enter Admin Password -> Verify (server-side) -> Reset, with a clear
final success/error message.

HOW PASSWORD VERIFICATION WORKS: the backend attempts a real Supabase Auth
sign-in with the provided password (using the public anon key, not the
service-role key) — this is the ONLY correct way to verify a password
without storing or reimplementing any credential handling, since Supabase
Auth is the sole owner of credentials in this architecture. A failed
attempt returns "Incorrect password" and NOTHING is deleted. This does
create a throwaway Supabase Auth session as a side effect (Supabase's API
has no "check password without a session" endpoint) — it's discarded
immediately and never stored or returned to the client.

WHAT GETS DELETED (in this exact order, inside one atomic transaction):
  picklists -> sales_returns -> transactions -> payments -> invoices ->
  sales -> import_jobs -> expenses -> salesman_customer_assignments ->
  customers -> invoice_number_sequences
(Several of these cascade further automatically via existing ON DELETE
CASCADE constraints — e.g. deleting sales also removes sale_items.)

WHAT IS NEVER TOUCHED: users (including the admin account), roles,
permissions, role_permissions, products, expense_categories, tasks.

HOW THIS WAS VERIFIED (not just reasoned about on paper): I built a real
foreign-key-enforcing test database, seeded EVERY dependent table
(picklists, sales returns, cheques, both transaction types, import job
rows, salesman assignments, invoice sequences), ran the actual deletion
sequence from admin_service.py against it, and confirmed:
  - zero foreign key violations
  - every "preserved" table survived with its data intact
  - every "wiped" table (including cascade-deleted children like
    sale_items and cheque_details) ended up empty
This is the strongest verification of any single piece of logic in this
project — the order isn't a guess, it's a traced dependency graph that was
then proven against a real constraint-enforcing database.

ONE THING I COULD NOT TEST: the actual Supabase Auth sign-in call, since
this sandbox has no real Supabase project to verify a real password
against. The code follows the same pattern your login flow already uses,
but please test this specific step for real — try Reset Data with a wrong
password first (should fail cleanly, nothing deleted) before trusting it
with a correct one.
